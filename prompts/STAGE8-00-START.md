## القاعدة الأولى: مرحلة واحدة في كل جلسة

```
/clear          ← تفريغ السياق قبل كل مرحلة
اقرأ prompts/STAGE8-01-sheets.md ونفّذه بالكامل. ابدأ الآن.
```

بعد انتهاء المرحلة و commit: `/clear` ثم المرحلة التالية.

**بدون `/clear` يبقى سياق المرحلة السابقة محمولاً في كل رسالة من التالية** —
وهذا أكبر مصدر لهدر التوكنز في المشاريع الطويلة.

## اختيار النموذج — قاعدة الجودة أولاً

المخرج النهائي لازم يطابق النموذج البصري **100%**. لذلك:

**استخدم Opus في:**
- أي مرحلة تنتج **واجهة يراها المستخدم** — المراحل 1 · 2 · 5 · 6
- أي منطق مالي أو قاعدة بيانات — المراحل 3 · 4
- التحقّق النهائي

**استخدم Sonnet في:**
- المرحلة 7 (الخط · PDF · PWA) — إعدادات وقوالب لا تصميم واجهات
- تكرار نمط **بعد** اعتماد شكله في صفحة أولى (انظر المرحلة 1)
- البحث والاستبدال النصّي البحت (تغيير نص · حذف `console.log`)

**لا تستخدم Sonnet في أي شيء يغيّر تخطيطاً أو مسافات أو أيقونات.**
توفير 20٪ من التوكنز مقابل واجهة غير متّسقة = خسارة، لأن إصلاحها لاحقاً
يكلّف أكثر مما وفّرته.

### التصعيد

بدأت بنموذج أرخص وفشل **مرّتين** في نفس المشكلة → توقّف فوراً، اعرض
المشكلة والملفات وما جُرّب في ثلاثة أسطر، وانقل المهمة لـOpus.
لا تكرّر المحاولة أربع وخمس مرات — هذا أغلى من التصعيد نفسه.

## وضع التنفيذ

`Shift+Tab` يبدّل بين وضع الموافقة على كل تعديل ووضع التنفيذ التلقائي.
داخل مرحلة واضحة المعالم، وضع التنفيذ التلقائي أوفر — لأن كل طلب موافقة
دورة رسائل إضافية. تأكّد أن git نظيف قبلها، فـ`git diff` مرجعك.

## قواعد اقتصاد التوكنز (سارية في كل المراحل)

1. ابحث أولاً (Grep) ثم افتح **الملفات التي ظهرت فقط**.
2. لا تفتح ملفاً «لفهم المشروع أكثر».
3. لا تقرأ `node_modules` · `vendor` · build outputs · lock files.
4. لا تقرأ كل الـmigrations — واحدة أو اثنتان تكفيان لفهم الـschema.
5. لا تعِد قراءة ملف قرأته في نفس الجلسة إلا إن تغيّر.
6. لا تشرح الكود، ولا تعرض محتوى ملف معدَّل، ولا diff كامل.
7. لا تشغّل الاختبارات كاملة بعد كل تعديل — الاختبار الأخصّ أولاً:
   واجهة → `npm run build` · خدمة → اختبارها وحدها · migration → `migrate`.
   الاختبارات الكاملة في نهاية المرحلة فقط.
8. commit **بعد كل مرحلة مكتملة** لا بعد كل تعديل.
9. لا تنشئ توثيقاً إضافياً ولا تعليقات تفسيرية طويلة داخل الكود.
10. إذا كان المطلوب واضحاً، نفّذه بلا طلب تأكيد.
